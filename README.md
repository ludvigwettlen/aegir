# Aegir

Aegir is a local-first macOS workspace with two main surfaces: a keyboard-first task list whose tasks you can hand to an agent team, and Slack-style group chats with agents organised into threads. Scheduled routines, Slack and Notion connectors and durable memory support both. This is a new runtime; Hermes was used as product inspiration only.

The default team is Aegir (lead and general assistant), Mimer (research and evidence), Saga (writing and communication), and Freja (product strategy and CPO advice). Freja advises on the products you build, challenging assumptions and weighing priorities, tradeoffs, and validation. Existing default agents are renamed in place on startup, preserving history, memory identities, and custom instructions.

Agent model routing: the Lead role uses the Codex account default. Mimer, Saga, Freja, and any other non-Lead agent use an available Luna model at low reasoning effort; routines use the tier of the agent that runs them, and choosing a group for a handed-off task uses the lightweight tier. The app checks `model/list` before these runs and reports an error if no supported Luna model is available, rather than silently using a larger model. Personal discovery and suggestion review use the account default model. Model choices are not yet individually editable.

## Run

For development, requires macOS, Node 20+, and pnpm. Run `pnpm install`, then `pnpm dev`. Build a local `.app` with `pnpm build`; it appears under `release/mac-arm64/Aegir.app` on Apple Silicon. `pnpm dist` packages the last build as a DMG. These builds have no Apple Developer ID signing or notarization; office testers may need to allow the app in macOS Privacy & Security, subject to their organization's device policy.

### Guided setup

A fresh workspace opens a four-step guide: choose Aegir or Legolas, check the selected AI, check memory, then review connections. Existing installations keep their Aegir setup, even with Claude installed. **Settings → Getting started → Continue setup / Review setup → Choose your setup** changes providers. The explicit choice, current step and dismissal/completion are saved outside the application bundle. New workspaces and provider changes keep automatic routines, Gmail discovery, and calendar checks paused until setup is completed; Set up later keeps manual task management available and preserves an unmade choice across restarts.

- **Codex:** detects existing installations, or downloads a private copy with **Install Codex**. **Sign in with ChatGPT** opens the app-server's browser authentication flow; Codex manages its credentials. Cancellation, retry, and account/model-catalog checks are available. Setup checks that the required Luna model appears in the account's catalog; this does not make an inference request or guarantee quota. `CODEX_BINARY` overrides the saved `codexBinary`, followed by detected desktop bundles and standard CLI locations.
- **Memory:** **Set up memory** downloads a private uv installer, managed Python 3.12, and `mnemosyne-memory[embeddings]`. No system Python, Homebrew, Node, shell commands, or administrator password is required from the user. Installation verifies save/recall/delete against disposable memory storage before saving `mnemosyneBinary`; it does not replace existing memory banks. Existing installations are checked and reused without reinstalling. First-time search can download embedding-model data.
- **Connections:** Notion uses the existing browser authorization flow. Slack can connect through a user's existing Composio consumer account, with optional office Slack app credentials in a disclosure. A connected Composio hub does not prove Slack access; test a Slack search. Gmail and Calendar still need an assisted Composio CLI setup; verify Gmail in Settings and Calendar in 1:1 prep. They are optional and never block completing onboarding.

**Legolas setup** uses an existing Claude Code installation/account and an existing Obsidian/gbrain brain. Aegir does not install those dependencies. Select the brain folder and, under gbrain routing, its registered brain/source IDs. Every search and memory write checks `gbrain sources list --json --brain <id>` against the selected folder. Searches explicitly pass both `--brain` and `--source`; writes append to `inbox/aegir-memories.md` in that folder. Your existing gbrain workflow must index/file the inbox. Edit/delete brain pages in Obsidian; Aegir does not rewrite indexed pages. Brain memory is shared context, with agent scopes recorded as labels, not isolated memory banks.

Claude runs use the installed user's connections and app tools, with app approval prompts for chat changes and shell commands. Unattended runs deny writes to external connections; annotated read-only tools are available. Native file writes stay inside task output folders. Shared delayed-send cards support configured Claude connections and Aegir delivery; live Claude connector delivery still requires validation with a signed-in account. Quick classification/routing runs have no tools or user connections. Default-tier replies use Claude Code's default model; lightweight work uses Sonnet. Account checks do not make a paid model call or verify quota.

Switching is blocked while agents, approvals, memory operations or tracked background work are active. It keeps tasks, chats, account settings and memory stores; it does not migrate memories or import/export brain tasks/documents. Legolas suppresses built-in task discovery without changing saved routine enablement. Other routines and existing Gmail/Calendar integrations remain configured. Optional task intake/export and per-file brain filing are available in Settings; external routine display remains a subsequent slice. Shared draft cards now include a five-second send countdown, Undo and manual-send status; Claude card delivery supports the fork’s native Slack and Superhuman Mail connections, with live account validation still pending.

Managed binaries and Python live under `<Electron userData>/runtime`; memory data and Codex credentials retain their providers' existing locations. Installers pin Codex 0.162.1, uv 0.13.1, and Mnemosyne 3.15.1. Codex/uv archive SHA-256 values are checked before extraction. Downloads and commands are time-bounded, duplicate installs are rejected, normal failures clean their new directories, and quitting cancels the installation before shutdown. A retry never deletes an existing installation or its data. Python and the Python packages are fetched from their normal upstream distribution services; transitive Python dependencies are not fully locked. The architecture-specific assets support Apple Silicon and Intel Macs; the real installer smoke checks were performed on Apple Silicon.

Implementation: `electron/onboarding.ts`, `electron/setup-install.ts`, and `src/ui/views/OnboardingView.tsx`. Run the focused tests with `pnpm test electron/onboarding.test.ts electron/setup-install.test.ts electron/codex-startup.test.ts`; the mocked browser walkthrough is `AEGIR_UI_SMOKE=1 pnpm test electron/onboarding-ui.test.ts` (Chrome and localhost access required). Live account authorization and workspace permissions still need a tester's own account.

The app keeps its window in the menu bar when closed. Packaged builds register as a background login item on first launch; the toggle is in Settings. Routines run on their schedule while the process is running and the Mac is awake; slots missed while asleep collapse into one run after wake.

For startup failures, including a running process with no window after a saved-credential decryption error, see [Troubleshooting](docs/troubleshooting.md).

## Connections

### Browser

Settings → Browser → Enable browser makes browser tools available to new chat and task responses. Google Chrome must be installed. **Open browser to sign in** opens a visible, separate Aegir profile; sign in directly there. Your usual Chrome profile is never attached. The first browser action in each response asks for permission to read signed-in pages and interact with websites, including form submissions and other changes. Denying the request blocks browser access for that response. Unattended routines do not receive these tools.

One agent controls the profile at a time. **Stop browser** revokes the current grant and closes Chrome; stopping the task or chat response also closes it. Finishing a response closes its tabs but keeps logins under `<Electron userData>/browser/profile`. Captures use a bounded cache under `browser/captures`. Access is off by default and can be disabled at any time. An approval grants browser interaction for the requested work; it does not change shell, file, Slack, or Notion permissions.

The backend uses pinned Playwright MCP tools for navigation, accessibility snapshots, clicks, typing, selection, tabs, dialogs and screenshots. Tool images are delivered to the model as images. Arbitrary JavaScript execution, uploads, agent-selected output paths and automatic downloads are not exposed. This release implements browser use; native desktop control is a separate follow-up.

To check the real browser integration without accounts or external websites, run `AEGIR_BROWSER_SMOKE=1 pnpm test electron/browser-smoke.test.ts --pool=forks --maxWorkers=1`. It uses a disposable profile and localhost page to verify interaction, screenshots, persistent cookies and reopening. If `better-sqlite3` is built for Electron, run the suite with `ELECTRON_RUN_AS_NODE=1 node_modules/electron/dist/Electron.app/Contents/MacOS/Electron node_modules/vitest/vitest.mjs run --pool=forks --maxWorkers=1`.

### Connected services

- Slack: create an **internal** Slack app with MCP enabled. Add `http://127.0.0.1:8765/callback/slack` as its OAuth redirect URL, and enter its Client ID and Client Secret in Settings. The app requests user-token search and history scopes, then opens Slack's OAuth flow. Your workspace admin may need to approve the app. [Slack's setup and scope guide](https://docs.slack.dev/ai/slack-mcp-server/).
- Notion: click Connect in Settings and complete the browser authorization. Available tools are discovered on connection, since Notion capabilities vary by workspace. [Notion MCP guide](https://www.notion.com/help/notion-mcp).
- Mnemosyne: install `mnemosyne-memory[embeddings]` in an isolated environment. Aegir detects `~/.local/share/aegir/mnemosyne-venv/bin/mnemosyne`, a Hermes installation at `~/.hermes/hermes-agent/venv/bin/mnemosyne`, or `mnemosyne` on `PATH`; the `mnemosyneBinary` setting overrides discovery. Mnemosyne is the only active memory store, with separate banks for shared and per-agent memories. The Memory screen searches those banks directly. An optional `hermesMemoryDataDir` setting (for example `~/.hermes/mnemosyne/data`, stored as an absolute path) adds Hermes’s default bank as a read-only retrieval source, labelled `[hermes]` in results. Chat, task and routine runs recall from the shared bank and the running agent's own bank, and expose a read-only memory search tool. Old Aegir SQLite memories are migrated into Mnemosyne on startup or the next memory operation; an unsuccessful migration leaves the original row intact and shows the remaining count on the Memory screen. Memory operations fail clearly while Mnemosyne is unavailable. [Mnemosyne CLI reference](https://github.com/mnemosyne-oss/mnemosyne/blob/main/docs/cli-reference.md).

OAuth tokens and the Slack secret are encrypted with Electron `safeStorage` on macOS. App state is in Aegir's Electron user-data directory as `aegir.sqlite`. On first launch after the rename, an existing Agent Desk database is copied into the new location. No connector credentials are committed to this repository.

## Product notes

**UI feedback.** Click **UI comments** at the bottom left, then click an element and describe the change you want. Selection blocks the element's normal action. Use **Stop selecting** to navigate, **Select element** to add another note, or **Comment on page** for general feedback. Escape stops selection; a second Escape exits the mode. **Comments** lets you review open/resolved notes, resolve or reopen them, refresh external changes, and **Copy for Codex**.

Comments are saved in `ui-feedback.json` in Electron's user-data folder (normally `~/Library/Application Support/Aegir` in the packaged app, or `~/Library/Application Support/aegir` in development). The inbox displays the actual path. Tell the coding assistant to read that file, or paste the copied brief into your chat. Saving comments does not start an agent automatically. Each comment includes the route, element label/selector, viewport and bounds; input values and screenshots are excluded. When working from the file, preserve all entries and IDs, and set an addressed comment's `resolvedAt` to an ISO timestamp after verifying the change (`null` reopens it). Refresh the inbox to see external updates. The JSON format is `{ "version": 1, "comments": [...] }`; avoid concurrent file edits while saving from the app.

Validate UI feedback with `pnpm test electron/ui-feedback.test.ts` and `AEGIR_UI_SMOKE=1 pnpm test electron/ui-feedback-ui.test.ts --pool=forks --maxWorkers=1` (Chrome and localhost access required).

**Fonts.** Open Settings (`Cmd+,`) → Fonts to choose separate fonts for the system UI and Markdown document content. Changes apply immediately and persist across restarts. Nine choices work offline; Reset to default restores Inter for both. Code and logs remain monospace.

**Tasks.** Inbox holds unfiled tasks. Create custom lists with **+** beside **My lists**, then press `M` on a task to open the move picker; browse with `J/K`, type to search, and press Enter to move tasks; `⌘Z` undoes a move. Quick-add creates tasks in the current list. Lists can be renamed or deleted; deleting a list returns its tasks to Inbox and preserves their conversations. Filing undated tasks removes them from Today, while due dates still surface in Today and Upcoming. Needs you collects suggestions, work ready for review and blocked work; Delegated shows tasks with an agent conversation. Tasks are grouped by label. Quick add understands multiple hashtags (`#work #board`) and date words (`today`, `fri`, `2026-10-02`). Add `every day`, `every weekday`, `every week`, or `every month` in quick add, or open **Repeat** at the top of task details and choose a schedule in the modal. Repeating tasks default to a due date of today. Completing one preserves its history and creates the next open occurrence with the same notes, labels, list and attachment; conversations and generated output remain with the completed occurrence. Missed dates are skipped, and monthly repeats retain their original day (clamped in shorter months). `⌘Z` undoes completion and removes an unchanged next occurrence. Reopening completed history does not create a second next occurrence. Choose **Does not repeat** on the current open occurrence to stop repeating. Hold `§` to see shortcuts for the current page or editor; release it to dismiss.

Agents in chats and handed-off tasks can edit or dismiss pending proposals when asked, using local task tools without browser approval. Edits cover title, notes, labels and due date; accepted tasks cannot be changed through these tools. Dismissal preserves source attribution and the deduplication record. Both edits and dismissals support task-list undo. Scheduled routines retain read and suggest access only.

**Handing off.** `A` takes one instruction. The task always goes to the agent team: a lightweight model picks the best group, and the group's lead starts in a new task thread. For substantive work, the lead is instructed to involve the most suitable teammate for a focused contribution or review; clearly simple tasks and requests to work alone can stay with one agent. The runtime executes one teammate follow-up in the same thread and output folder before moving the task to review. File deliverables go into `~/Documents/Aegir/<task>` (Codex `workspace-write` sandbox with that folder as its working directory). Slack and Notion tools remain read-only. When Browser is enabled, tasks may also request browser control for that response; website changes require that separate approval. When the run ends the task moves to Needs you for review; replying in its thread continues the work. Click the task’s channel label or press Shift+A on its row to open that exact conversation in the channel.

**1:1 prep.** Open **Meetings → 1:1 prep**, enter the alias of your existing Composio Google Calendar account, and enable automatic preparation. This requires the authenticated Composio CLI at `~/.local/bin/composio`; the calendar connection is independent of Aegir's Slack/Notion MCP connections. Aegir reads the primary calendar every 30 minutes while open, paginates the next seven days, and recognizes explicit 1:1 titles or pairs of names with exactly two human invitees. Declined, all-day, cancelled and group events are excluded; rooms are ignored. Calendar access uses only GET requests to Google's [events list API](https://developers.google.com/workspace/calendar/api/v3/reference/events/list), with recurring events expanded into individual meetings.

Agendas are prepared automatically within 36 hours, one at a time, using the account default model and read-only Slack, Notion, task and memory tools. Each preparation recaps previous conversations from the attendee's Notion 1:1 notes and relevant Slack exchanges, identifies open follow-ups, and suggests 2–4 agenda topics with source links and coverage limits. Notion remains the home for meeting notes; Aegir has no meeting-notes editor or post-meeting workflow. Legacy local notes are retained but excluded from preparation, as are previously generated agendas. Use **Prepare now** for a later meeting or **Refresh agenda** for updated context. Failed preparations retain the prior agenda and can be retried manually. Calendar changes mark agendas stale; cancelled/missing events leave the upcoming list. Hide/Restore corrects false positives. Agenda edits are saved locally, unsaved drafts survive navigation and restart, and automatic preparation preserves user-edited agendas. An explicit refresh keeps the previous agenda below the current version. Automatic checks pause when Aegir quits and resume on launch/wake; no separate system scheduler is installed.

**Groups and threads.** A group is a standing set of agents with an optional purpose; each agent also has a private group for direct chat. Conversation happens in threads, and each run sees only its own thread's transcript plus recalled memory, which keeps context bounded. Mentioning `@Agent` brings that agent in. Chat runs can use Slack and Notion writes, each behind an in-app approval.

**Routines.** Scheduled agent runs (hourly, daily or weekly, optionally weekdays only), listed in the sidebar. Each run is a Codex conversation with read-only connector tools, memory, and `tasks__suggest` for putting items under Needs you. Every step is written to a run log (raw text, kept for 30 days) that you can open from the routine. Tag a routine in chat (`@Hourly discovery`) to discuss it; agents can propose a change or a new routine, which you apply or discard. Approval requests during unattended runs are declined and logged. The seeded "Hourly discovery" routine finds only new, concrete actions personally owned by the user. It uses the account default model, recalls stable user context while excluding identified past discovery reports, and cannot write durable memory; findings stay in run logs. Existing seeded discovery prompts are upgraded once while preserving connector instructions, schedules and agent assignments. Every routine suggestion must supply primary-source ownership and freshness evidence and pass a separate review against the complete task history, including dismissed and completed tasks. Review compares intended outcomes rather than titles, allows distinct actions from the same source, and rejects uncertain or invalid reviews. Routine Slack reply/read/acknowledgement reminders are excluded even for explicit unanswered questions: Slack already handles conversation triage. Substantive deliverables or decisions from Slack can still qualify, titled for their outcome. Both discovery and independent review enforce this distinction; a review must explicitly classify Slack reply-only work, and missing classification fails closed. The separate Gmail reply inbox is unchanged. This adds one model call per new candidate. A history exceeding the review context budget blocks creation explicitly rather than silently skipping older tasks.

Codex runs chat and routines in a read-only sandbox. Commands that need broader permissions pause for an in-app approval. The app does **not** implement a separate policy engine that can classify every possible credential read or app-automation command; do not grant a broad command approval without inspecting it.

Upgrading keeps existing data: rooms become groups, each room's history becomes a closed "Earlier conversation" thread, and goal output becomes a task thread. The old tables stay in the database. No Slack, Notion, or Mnemosyne account was connected during local development, so live OAuth, retrieval and full agent runs need an end-to-end check with your accounts.

The in-app Markdown workspace supports formatted editing, autosave, and selected-passage references to the team. The active heading shows its `#` level in the left margin. Type `/` on an empty paragraph to insert a table, link, list, checklist, quote, code block, or divider; Cmd+K opens link insertion for selected text.

Choose **New document** in a task or its Files picker to create an empty Markdown file and open it for editing. Enter a filename; `.md` is added automatically when omitted. This works before handoff, without running an agent, and the team uses the same folder when you hand the task off later. Existing filenames are rejected without overwriting content.

**Documents.** Click a document row in a task preview to open the editor directly. The preview shows the three most recently updated files; **View all** opens a searchable picker. Switch files from the editor title, toggle **Chat** when needed, and use **Back to list** or Escape to save and return. Chat drafts, document positions and panel preferences are retained.

The UI is documented in [the design system](docs/design-system.md).
Current follow-up work is tracked in [TODO.md](TODO.md). Shared agent behavior and the Hermes comparison are documented in [the instruction review](docs/agent-instructions-review.md).

## Verification

`pnpm test` uses Electron’s Node runtime so SQLite matches the app after a build. The packaged app requires macOS 13 or later.

`pnpm check` runs TypeScript validation. `pnpm test` covers the store migration, hand-off and routine runs against a fake Codex, the read-only tool policy, routine schedules and change validation, quick-add parsing and task lists. `pnpm build` compiles and packages the macOS app.

Tests should protect observable outcomes, permission boundaries, data preservation, and distinct failure paths. Avoid locking prompt wording or seed counts. Assertions for asynchronous failures must run outside error-catching application callbacks so a swallowed assertion cannot produce a passing test.

## Skills

Open **Settings** with `Cmd+,` or the Aegir menu, then **Manage skills** to manage shared skills, agent-owned skills, proposed changes, and archives. Shared skills are inherited by default and can be disabled per agent. Create or import a `SKILL.md` file or complete skill folder; supporting references and binary assets are preserved. Bind required skills in a routine’s Skills section. Type `/` in a conversation composer to search skills available to its current recipients. Enter, Tab, or clicking selects a skill; removable chips show what will be loaded with the message. Explicit selections use stable IDs, and the runtime rechecks scope and requirements before loading.

Chats, tasks, and routines share on-demand discovery and loading. Each run reads a frozen package revision. Agents may create and refine their own learned skills; shared, imported, and user-authored changes are proposed for review. You can protect a skill from agent changes, compare proposals, restore revisions, customize shared skills for one agent, or promote an owned skill to a shared copy. Skill instructions never grant additional tool permissions.

Live packages are under `<Electron userData>/skills`; SQLite stores scope, bindings, full revision snapshots, change proposals, usage, and recovery journals. Direct disk changes are reconciled before runs and when opening the library. Agent scope controls discovery and tools, not OS-level confidentiality. Script execution helpers, remote skill marketplaces, and automated curation are not included in this release. See [the architecture](docs/skills-architecture.md) for details.

### Slack through Composio

In Settings → Connections → Slack via Composio, enter the expected Slack connection ID and the **consumer API key from Composio's AI Clients setup** (not a Platform project API key), then Connect. Alternatively leave the key blank and authorize the same Composio account in your browser. Disconnect clears Aegir's saved Composio credentials; it does not revoke or delete your upstream Slack connection. Disconnect before switching from a saved key to browser authorization.

The endpoint is fixed to `https://connect.composio.dev/mcp`; credentials use encrypted macOS storage and are never included in snapshots or model prompts. The hub resolves the active Slack connection. The expected account ID is included in tool guidance so agents check discovery results; it is not a server-side pin. Other connected apps are not executable through this integration.

Agents can discover Slack tools and use a locally validated read-only execution wrapper in chats, tasks, and routines. Other Slack actions use the existing chat approval flow; tasks and routines cannot execute them. Unknown read actions require chat approval until added to the reviewed allowlist. Remote bash/workbench and connection-management tools are excluded. Authenticate and test a Slack search before enabling unattended work; an MCP connection alone does not prove the Slack account is active.

References: [Composio Connect](https://docs.composio.dev/docs/composio-connect), [consumer-key header](https://docs.composio.dev/kb/guide/toolkits-linkedin), [meta tools](https://docs.composio.dev/toolkits/meta-tools).

### Gmail through Composio

Settings → Gmail via Composio accepts an existing Gmail account alias and its expected email address. Aegir uses `~/.local/bin/composio proxy` and verifies the Gmail profile before access; this is independent of the Slack-only Composio MCP connector. No Gmail OAuth token is stored in Aegir. The connected Gmail account needs read and send permissions. New agent responses receive `gmail__search`, `gmail__read_thread` and (in chats/tasks) `gmail__draft`, even with a read-only filesystem sandbox.

Automatic reply discovery runs every 15 minutes while Aegir is running. It checks read and unread inbox threads from the last 30 days (up to 250), excludes calendar, bulk, promotional, social, forum and update mail, and asks the model to identify a clear personal response obligation from the current thread. Positive decisions are re-read before saving ready tasks in Inbox. Source keys include account, thread and incoming message; open tasks and completed/dismissed requests are deduplicated. A new incoming request can create a new task after completion or dismissal. Observed sent replies finish ready/proposed reply tasks. Existing tasks survive scan failures. Gmail settings show coverage, last check and errors. Classification is conservative and can miss ambiguous requests; Gmail remains the source of truth.

Email assistance opens a local inline draft with To/Cc/Bcc/Subject/Message. Save draft keeps it in Aegir. Clicking **Send** saves edits and explicitly approves that exact revision and content; there is no second approval popup. The main-process send path is unavailable to agent tools, records the approval time and revision, and locks the draft against changes or duplicate sends. It rechecks the account, preserves reply headers, and marks ambiguous deliveries as uncertain without retrying. No attachments or rich HTML are supported yet. This gate covers Aegir's Gmail send path; it is not an operating-system restriction on independently authorized shell or browser access. Agents are instructed to use this path for email and never bypass it.

### Inline Slack messages

Ask for help drafting a Slack message in a chat or task to open the inline editor. It shows the verified workspace, sender and destination, and the parent message for thread replies. Edit the text or use **Change recipient** to search people and channels. Save draft keeps a local Aegir draft; unsaved text survives navigation. Messages are plain text, without attachments or automatic link previews. **Include “Sent using Aegir” footer** is checked by default for each draft; uncheck it to omit the attribution. The editor previews the footer and remembers the choice through saves and agent edits. Your Send click approves the message and footer together.

The composer uses the Composio CLI and the existing Slack account alias in Settings. It verifies the Slack workspace and user and resolves destinations before saving. Clicking **Send** is the approval: the backend checks the displayed fields and revision, records approval, rechecks identity and destination, and sends once. Opening a new direct-message conversation is deferred until Send. Failed preflight or explicit Slack rejection can be corrected; uncertain delivery locks the draft and asks you to check Slack before composing another message. Agents have draft and edit tools but no composer send tool, and direct Composio message-send actions are blocked in favor of the editor. Other Slack changes retain their existing approval flow. Unattended routines cannot use the composer.

For tests against the Electron-built SQLite dependency, use `ELECTRON_RUN_AS_NODE=1 node_modules/electron/dist/Electron.app/Contents/MacOS/Electron node_modules/vitest/vitest.mjs run` if the system Node ABI differs.


**Clearing task attention.** For a task ready for review or blocked, choose **Mark reviewed** (the double-check icon in its toolbar, or the command palette). This removes it from Needs you and keeps it Open, with its conversation, documents and task details intact. Undo with ⌘Z. New agent work can bring it back to Needs you. Suggestions still use Accept/Dismiss; marking reviewed never completes a task or creates its next repeat.


**Priority visibility.** Settings → Task priorities → **Show task priorities** is on by default. Switch it off to hide priority controls, badges and shortcuts. This preference is saved on this computer; existing task priorities are preserved and shown again when enabled.

### External Claude workflow and brain filing

In **Settings → External workflow and brain filing**, select separate existing folders and explicitly enable the integrations you want. No integration is enabled merely because a brain folder exists. Legolas offers task import and export; both Aegir and Legolas offer per-file brain copies. Switching back to Aegir pauses external import/export while retaining the saved configuration. Background checks run once per minute only while the app is open and setup is finished; **Check now** runs the same bridge immediately.

External routines publish one JSON object, an array of up to 100 objects, or one Markdown suggestion per file in the intake folder. Use `.json` or `.md`, with a maximum of 1 MB per file. Files must be unchanged for two seconds before intake; producers should write a temporary file and atomically rename it into place. A pass handles at most 50 files and 8 MB, leaving the rest for later.

```json
{
  "title": "Reply to Sarah’s proposal",
  "notes": "Sarah needs a decision before Friday.",
  "sourceKey": "slack:T123:C123:1792576800.000001",
  "sourceUrl": "https://example.slack.com/archives/C123/p1792576800000001",
  "labels": ["work", "board"],
  "dueAt": "2026-10-23"
}
```

`title` and a stable `sourceKey` are required; all other fields are optional. Keys must identify the original request consistently across reruns and include account/workspace context. Reuse an existing Aegir source key when referring to an already-known request. A genuinely new request needs its own key. Markdown uses the same fields in YAML front matter and the document body as notes:

```markdown
---
title: Reply to Sarah’s proposal
sourceKey: slack:T123:C123:1792576800.000001
sourceUrl: https://example.slack.com/archives/C123/p1792576800000001
labels: [work, board]
dueAt: 2026-10-23
---
Sarah needs a decision before Friday.
```

Imports become proposals in **Needs you**, with source identity retained. A whole file is validated before any of its tasks are created. Stable-key receipts survive completion, dismissal and deletion, including when a matching source was already in Aegir. Re-imports leave the existing task’s title, notes, date, status and manual priority intact. Different keys are treated as different requests; the bridge does not run another AI relevance or duplicate gate. External priorities, updates and closes are not accepted by this suggestion-only contract.

Successful inputs move to `processed`; invalid files move to `rejected` with an error note. Settings shows imported/skipped/rejected/deferred counts and errors. Failed archiving preserves duplicate receipts, so retrying cannot create tasks twice. Intake does not execute commands or interpret notes as instructions.

Task export writes `aegir-tasks.json` (a version-1 object containing `tasks`) and `aegir-tasks.md` to the chosen export folder. The JSON includes IDs, source keys/links, titles, notes, statuses (including completed and dismissed), priorities, dates, list IDs, timestamps and local output-workspace paths. External routines can read the workspace path to inspect generated results. These are generated snapshots: edit tasks in Aegir. Files are replaced atomically and rewritten only when their content changes. They do not include conversation transcripts, attachment contents or memory stores.

**File to brain** appears on open documents and sent conversation attachments after enabling filing. Document edits must save successfully before copying. Each explicit click copies the selected file to the chosen folder under a unique name, preserving the original and existing destination files. Only that file is copied; linked files and document images stay in the task workspace. Filing does not index, reorganize, mirror future edits or commit the brain. gbrain search/memory availability still needs validation against a configured installation independently of this file bridge.

**Snooze and staying on a task.** Use **Snooze** in task details, press **S** outside a text field, or choose Snooze in the command palette. Pick Tomorrow, Next week (next Monday), or a future date. Snooze hides ready/review/blocked tasks from active and custom lists until that local date, while keeping their real due date, priority and repeat schedule. Find them in Upcoming and choose **Unsnooze** to bring them back early. Snoozes persist across restarts and support task Undo. Date-dependent lists refresh every 30 seconds and when the app regains focus.

Changing a task’s date, list or snooze can remove its row from the view you are using. Its details stay open so you can finish editing; an explanatory notice offers **Back to list**. Selecting another task or switching views also releases it. Completing, dismissing or deleting a task keeps ordinary next-task navigation.

### Task capture, planning and personal integrations

- **AI capture** beside quick add uses your selected Codex/Claude engine to prepare a task. Review/edit its title and notes before adding. It has no tools or connection access. Your original note stays available if preparation or creation fails. Ordinary quick add remains available without AI.
- **Today** sets the task deadline to today and clears snooze. It works across custom lists and supports Undo. For repeating tasks, it updates the recurrence anchor through the existing deadline behavior.
- **Labels** supports up to 20 labels per task (40 characters each). Use Add labels/the label chip in task details or B to edit comma-separated labels and choose existing ones. Quick add accepts multiple hashtags. Labels are normalized and deduplicated; existing single labels carry over. Undo, recurrence, search, AI capture and task import/export retain multiple labels.
- **Filtered views** appear in the sidebar. Click + beside Filtered views or use Filter and sort in a task list. Choose a scope (all open tasks, a built-in view or a custom list), select labels with All/Any matching, and optionally filter status/priority and sort. Name it and Save view. Update view saves edits/renames; Save as new view copies it; Delete view removes only the view. Selecting it again restores its saved filters. Views persist in the local app database; previous local presets migrate automatically. Unsaved per-list filter preferences remain local. All open tasks includes suggestions and snoozed tasks; Completed is a separate scope.
- **Settings → Personal integrations → Apple Reminders capture** imports non-repeating reminders from the named list, with either engine setup. Capture starts disabled. Save the list and enable it, then Check now or wait for the minute check after setup is complete. Captures become ordinary tasks; this is not bidirectional task synchronization. Imported reminders are completed only after their timed/date alerts can fire; location or unschedulable alerts stay in Reminders. Reopened/deleted task captures are remembered, preventing re-import. Duplicate list names are rejected. macOS permission is requested by the native helper on first check.
- **Refresh external routines** displays supported Claude desktop schedules and recent run results, read-only, with either setup. Claude owns those schedules. Its local file format is not a public API; unsupported/missing data shows an empty result.

The macOS build compiles `native/reminders/main.swift` with EventKit and bundles the helper plus Reminders permission descriptions. The module cache stays under the ignored build folder. Live Claude/gbrain and connector checks still require configured accounts/tools; fixture checks do not validate a live delivery.
